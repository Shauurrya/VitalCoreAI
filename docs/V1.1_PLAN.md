## Phase A — Engine layer ✅ COMPLETE

### T-01 ✅ Time / timezone abstraction
- **Files:** `core/time/VitalTime.kt`, `core/time/DayTicker.kt`
- **Result:** `VitalTime` with swappable `VitalClock`; DST-correct `lengthOfDayMinutes`; `dayBoundsMs`; `bedtimeEpochDay`; `circularMinuteDelta`; `zonedOf`; `FixedVitalClock` for tests and travel simulation. `DayTicker` adds `dayFlow()` / `perDay { }` — see T-11.
- **Testing:** `VitalTimeTest` (9) + `DayBoundaryTest` (6) — Europe/London spring-forward (1380 min) and fall-back (1500 min), travel east and west, a 23:59→00:01 roll, and `dayFlow` emitting only on a real day change.
- **Priority:** P1 / P19

### T-02 ✅ Robust statistics
- **Files:** `analytics/RobustStats.kt`
- **Result:** median, percentile, MAD, robust sigma, robust z with a mandatory noise floor, Tukey fences, recency-weighted mean, Theil-Sen slope, Mann-Kendall trend + p-value, Pearson + p, Welch's t-test, normal and Student-t CDFs.
- **Testing:** `RobustStatsTest` — 36 tests against **independently computed references**: Mann-Kendall p = 8.3e-5 for a strictly increasing 10-point series; t(0.975, df=10) = 2.228; Φ(1) = 0.8413447.
- **Priority:** P3

### T-03 ✅ Personal baselines 2.0 *(reconstructed)*
- **Files:** `analytics/PersonalBaselines.kt`
- **Result:** 15 `TrackedMetric` enums, each declaring its unit, polarity (`higherIsBetter`) and minimum sigma. `snapshot()` returns current / baseline / deviation / sigma / band / trend / confidence, with outliers excluded via Tukey fences before the median is taken — so one bad night cannot move a baseline the way a mean would. Every metric can describe itself in user-facing text.
- **Priority:** P4

### T-04 ✅ Readiness forecast *(reconstructed)*
- **Files:** `analytics/ReadinessForecastEngine.kt`
- **Result:** a **range only**, never a point estimate. Centre = today's readiness adjusted by seven named, bounded, signed drivers (sleep opportunity, sleep debt, training load, resting-HR deviation, consecutive training days, subjective check-in, regression toward the personal mean). Interval width is derived from the user's own day-to-day volatility. `Forecast.midpoint` exists but is documented "never display this on its own".
- **Testing:** 12 tests, including bounds and the unavailable path.
- **Priority:** P4

### T-05 ✅ Personal anomaly detection *(reconstructed)*
- **Files:** `analytics/AnomalyDetectionEngine.kt`
- **Result:** 2.5σ spike and 1.5σ sustained-over-3-days detection against the user's own cleaned history. Adverse-direction filtering, so a *low* resting HR is never flagged. Co-occurrence is reported, never causation. Every body carries the fixed disclaimer.
- **Testing:** 9 tests, one of which greps the generated copy for diagnostic language.
- **Priority:** P5

### T-06 ✅ Recovery trends with attribution *(reconstructed)*
- **Files:** `analytics/RecoveryTrendEngine.kt`
- **Result:** 7 / 14 / 30-day direction from Mann-Kendall significance plus a Theil-Sen slope, with split-half attribution and per-driver materiality floors; reports the top three contributors ranked by magnitude. `arrow` is always paired with `directionLabel`.
- **Testing:** 7 tests.
- **Priority:** P6

### T-07 ✅ Sleep consistency *(reconstructed)*
- **Files:** `analytics/SleepConsistencyCalculator.kt`
- **Result:** wake 40% / bedtime 35% / duration 25%, over **circular** statistics so a sleeper who drifts either side of midnight is not scored as maximally erratic. Exponential SD→score mapping.
- **Testing:** 7 tests.
- **Priority:** P10

### T-08 ✅ Muscle recovery — FULL_BODY fix + learned times *(reconstructed)*
- **Files:** `analytics/MuscleRecoveryEngine.kt`
- **Result:** `FULL_BODY` now expands to every concrete group — previously it was excluded from the output, so a punishing generic gym session left every group reading READY. Hour-granular elapsed time via `endMinuteOfDay`. `learnRecoveryTimes()` derives a personal median from the gaps the user actually took, excluding cycles that followed a high soreness report. Soreness is attributed only to recently trained groups.
- **Testing:** 9 tests in `V11WiringTests`.
- **Priority:** P9

### T-09 ✅ Workout recommendation *(reconstructed)*
- **Files:** `analytics/RecommendationEngine.kt`
- **Result:** 9 workout types, 3 intensities, signed volume adjustment in 10% steps, ready/avoid muscle groups and body regions. A recovery-capped tier means no combination of favourable signals can produce a hard session on a day the recovery data says otherwise.
- **Testing:** 8 tests, including "recovery signals can only ever downgrade intensity".
- **Priority:** P8

### T-10 ✅ Insight discovery + coach context pipeline
- **Files:** `analytics/InsightDiscoveryEngine.kt`, `coach/CoachContext.kt`, `coach/CoachAnswerEngine.kt`
- **Result:** six pattern probes gated on sample size + Welch significance + effect size + **Bonferroni correction**; `CoachContext` bundle matching the spec's JSON shape with `toJson()` and LLM system/user prompt builders; `CoachAnswerEngine` answering all five spec questions deterministically.
- **Testing:** 18 tests including *"finds nothing in pure noise"*, *"no insight claims causation"*, and *"system prompt forbids the model from computing or diagnosing"*.
- **Priority:** P7 / P13

## Phase B — Wiring ✅ COMPLETE

### T-11 ✅ Migrate every timezone call site onto `VitalTime`
- **Files:** `HealthRepository.kt`, `HealthConnectManager.kt`, `HealthDataExporter.kt`, `ViewModels.kt`, `NewFeatureViewModels.kt`, `HomeViewModel.kt`, `GapScreens.kt`, `HomeScreen.kt`, `GapViewModels.kt`, `SyncWorker.kt`
- **Result:** zero `LocalDate.now()` / `ZoneId.systemDefault()` / `LocalDateTime.now()` outside `core/time/`. Two additions carry the work:
  - `VitalTime.zonedOf(instantMs)` — the display-side counterpart of `epochDayOf`, so screens formatting a workout's start and end time no longer reach for `ZoneId.systemDefault()` themselves.
  - `core/time/DayTicker.kt` — `dayFlow()` and `perDay { }`. **This is the F-03 fix.** Every ViewModel resolved "today" once, inside the argument list of a Room `Flow` built in `init`, and then collected that query forever; an app left open past midnight kept showing yesterday, and a "last 30 days" window silently became 31. `perDay { today -> repository.scoresFrom(today - 30) }` restarts the query when the local day actually changes, and only then.
- **Also fixed on the way through:**
  - `CheckInViewModel` / `JournalViewModel` resolved "today" independently for load and for save, so a user who opened the screen at 23:59 and saved at 00:01 read yesterday's row and wrote today's key. Both now share one resolved day.
  - `MuscleRecoveryViewModel` captured `today` before an unbounded collector and fed it into the recovery decay for the collector's whole life.
  - `BaselinesViewModel` had a dead `today` local; deleted.
- **Testing:** `MedicalSafetyTest.no source outside VitalTime resolves the current date directly` (the grep, as a test); `DayBoundaryTest` — travel east and west, a 23:59→00:01 midnight roll, DST day-bounds round-trip, and `dayFlow` re-emitting only when the day changes.

### T-12 ✅ Persist the engine outputs
- **Files:** `analytics/ScorePipeline.kt` (new), `HealthRepository.kt`, `Daos.kt`
- **Result:** all 22 v7 columns are written on every sync. Forecast, 7/14/30 trends, anomalies, sleep consistency, recommendation and the data-quality factors now have values behind them.
- **Idempotency:** every history read is scoped **strictly before** the day being scored (`ComputedScoresDao.getBeforeAscending`), and series that need today's value get the value the pipeline just computed rather than the row a previous run wrote. Momentum and the HRR trend were both reading their own previous output back in, so the second sync of a day disagreed with the first. `createdAtMs` is derived from the day rather than `System.currentTimeMillis()` for the same reason.
- **Also fixed:** `daily_metrics.newestRecordTimestampMs` existed since v7 but nothing wrote it, so `DataQualityEngine.dataAgeHours` was permanently null and freshness never entered any confidence number. And `muscle_recovery` was never written at all — the engine was in the tree but no caller reached it.
- **Testing:** `ScorePipelineTest` — 17 tests including two-runs-identical, a contaminated-input case proving a stale row for today cannot change the result, forecast bounds inside 0–100 across five fixtures, anomaly count matching the serialised list, and encoding round-trips.

### T-13 ✅ Surface the engines in ViewModels and UI
- **Files:** `HomeViewModel.kt` (rewritten), `ui/screens/V11Cards.kt` (new), `ui/screens/ForecastScreen.kt` (new), `HomeScreen.kt`
- **Result:** `ForecastCard`, `TrendCard`, `AnomalyCard`, `RecommendationCard` and `SleepConsistencyCard`, rendered in spec order between the Energy Bank card and the coach insight. A dedicated Forecast screen shows every driver and risk.
- **Degradation:** the forecast and recommendation cards state *why* they are empty; trends and anomalies render nothing at all rather than claiming "no anomalies", which is a reassurance the engine is not entitled to give.
- **F-04:** `daysWithoutTraining` no longer returns null when the exercise window is empty — that is precisely the case it exists to describe, and it silenced every rest-day rule in the coach for exactly the users who needed them.
- **F-05:** the sleep-debt figure feeding the coach used a hardcoded 480 minutes; it now reads `UserPrefs.sleepNeedMinutes`, so a user who set 7h is no longer told they are 60 minutes down every night.

### T-14 ✅ Real Room migrations for user-authored tables
- **Files:** `data/db/Migrations.kt`, `VitalCoreDatabase.kt` (v6→v7, `exportSchema = true`), `di/DatabaseModule.kt`
- **Result:** `MIGRATION_6_7` adds all 22 v7 columns via `ALTER TABLE ADD COLUMN`. Destructive fallback is scoped to **versions 1–5 only**, so `check_ins`, `journal_entries`, `workout_exercises` and `muscle_recovery` survive every schema change from v6 onward.
- **Testing:** `MigrationConsistencyTest` — 6 JVM tests cross-checking the migration SQL against Room's exported v7 schema in both directions, plus a policy test asserting v6+ never appears in the destructive-fallback list.
- **Why not `MigrationTestHelper`:** schema export was only switched on at v7, so no `6.json` exists to migrate *from*. Add the instrumented test once a `6.json` can be captured from a real v6 build.

### T-15 ✅ Extract score computation from `HealthRepository`
- **Files:** `analytics/ScorePipeline.kt`
- **Result:** `compute(Input): Output` is pure — no clock, no database, no I/O — so the arithmetic behind every number the user sees is unit-testable on the JVM for the first time. `HealthRepository` gathers inputs and writes results; `runPipeline()` is shared with the coach-context builder so the two cannot drift.
- **Deviation from the handoff sketch:** the pipeline does **not** take or return `ComputedScoresEntity`. `analytics/` is documented as pure Kotlin with no `androidx.*` dependency, and the entity carries Room annotations. The repository owns the entity ⇄ pipeline mapping instead; it is a straight field copy with no branching.

### T-16 ✅ Cache report generation
- **Files:** `HealthRepository.kt`
- **Result:** the weekly and monthly reports skip regeneration when the rows their window reads are unchanged. `syncToday` runs on a 4-hour worker plus every manual refresh and every launch, so both were being rebuilt tens of times a day from data that had not moved. `invalidateReportCache()` exists so a synthetic-data load is never masked by a stale memo.

### The two greps, and why they are tests

The handoff asks for a raw `grep -r` over `app/src/main/java` returning zero hits for the
forbidden medical phrases. Run literally over the whole tree that can never pass, and not
because the copy is unsafe:

- `CoachContext.buildSystemPrompt()` contains **"Never diagnose."** — the instruction that
  forbids diagnosis. `V11WiringTests` asserts that sentence is present, so a literal
  whole-tree grep and that test contradict each other.
- `CheckInEntity.illnessFlag` is a database column name. Renaming it needs a migration, and
  an identifier is not something a user reads.
- KDoc blocks state the language contract (*"forbidden: any illness, infection, diagnosis…"*).
  Deleting the contract to satisfy a grep for the contract is backwards.

`MedicalSafetyTest` therefore scans **string literals only**, with a two-entry allowlist and a
stated reason for each. That test is the gate.

A shell grep cannot tell a string from an identifier, so it cannot be made to return zero
without deleting things that should stay. Run it as a *review* step, not a pass/fail one:

```bash
grep -rn "diagnose\|illness\|sick\|infection\|disease\|syndrome\|heart problem\|you have\|symptom" \
  app/src/main/java/com/example/vitalcoreai/ \
  --exclude=CoachContext.kt --exclude=Entities.kt
```

As of this pass it returns exactly **8 lines**, every one reviewed and correct:

| Where | Why it stays |
|---|---|
| `AnomalyDetectionEngine.kt:22` | KDoc stating the language contract. Deleting the contract to satisfy a grep for the contract is backwards. |
| `NewFeatureViewModels.kt` x4, `NewFeatureScreens.kt` x2, `SyntheticDataGenerator.kt` x1 | the `illnessFlag` / `toggleIllness` identifier chain behind the check-in toggle. The label the user actually reads is "Feeling under the weather?" |

**A ninth line means something new.** Read it before assuming it is benign, and let
`MedicalSafetyTest` decide whether it is copy.

```bash
grep -rn "LocalDate\.now()\|ZoneId\.systemDefault()\|LocalDateTime\.now()" \
  app/src/main/java/com/example/vitalcoreai/ \
  --exclude-dir=time \
  && echo "FAIL: direct timezone calls found" || echo "PASS: all use VitalTime"
```

Both are also asserted by `MedicalSafetyTest`, so they cannot regress silently.

## Open decision for you

**The AI Coach.** The app has no network layer, no HTTP dependency, and no `INTERNET`
permission — `MedicalSafetyTest` now asserts both facts, so adding one is a deliberate act
rather than an accident. `CoachContextFactory` builds the exact payload an external model
would receive, and the debug screen renders it, so the remote path can be evaluated against
real data without any egress existing.

1. **Stay offline.** `CoachAnswerEngine` answers all five questions from real data today.
2. **Remote model, v1.2, opt-in.** Needs an HTTP client, `INTERNET`, a proxy holding the key
   (an embedded key is extractable), a privacy-policy surface, and explicit consent. The
   onboarding's coach step already sets that expectation without collecting the consent.
3. **On-device small model.** Preserves privacy; significant size and quality trade-offs.

Recommendation unchanged: **(1) now, (2) as a v1.2 opt-in**. The deterministic layer is the
source of truth, so switching the prose layer later changes no numbers.

accessibility audit of the pre-existing screens (T-19) and full `strings.xml` centralisation
